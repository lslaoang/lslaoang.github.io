A lending platform for a cooperative

The Spring Boot backend running a Philippine cooperative's entire loan book — member onboarding through collections, settlement, and audit. 267 Java source files, 300+ commits, containerized on Google Cloud.

Cooperative lending is small amounts to many borrowers, collected often, by people walking a market route. The loan maths is the easy part. The hard parts are keeping payment schedules correct as they age, organizing collection by where the borrower actually is, and being able to answer "who changed this record, and when" a year later.

  • Member credit profiles — personal and family background, employment, assets, debts, other income sources, bank details, and uploaded documents. The full picture an underwriter needs before approving anything.
  • Loans with co-borrowers and collateral, moving through explicit status transitions and closed out by a dedicated settlement service that writes ledger entries.
  • Payment schedules generated per loan, advanced by a scheduled status updater as due dates pass, with collection grouped by market.
  • A real audit trail — every state change captured as a Hibernate Envers revision and queryable through its own audit API, not reconstructed from logs.
  • Security and operations — JWT authentication with login-attempt lockout, Flyway-versioned MySQL migrations, Caffeine caching warmed on boot, and soft deletes so records survive their own removal.
  • Supporting documents stored through the Google Drive API; built and shipped as a Docker image via GitHub Actions.

DSV2026Freelance

An unattended kiosk that takes real money

A production self-service printing kiosk: print, scan, and copy on real Canon hardware, paid by coin, card, or QRPH, with phone uploads over a cloud relay. Ships to the machine through its own self-updater.

An unattended machine has nobody to apologize on its behalf. If it takes payment and the paper never comes out, that's a customer standing alone in front of a box. So the engineering went into refusing to claim success it can't verify: post-spool checks catch device-side blocks the driver reported as fine, a startup system check validates every device before the machine will trade, and failures surface as plain customer-readable screens instead of a crash.

  • Two ways in — print from a USB drive, or scan a one-time QR and upload straight from a phone browser with no app to install (iPhone HEIC photos convert automatically).
  • A scan workspace on the Canon LiDE 300 — repeat scans for multi-page jobs, rotate and delete pages, then any mix of printing, saving to USB, and sending back by QR under one combined payment.
  • Three payment channels — coin acceptor, card terminal, and QRPH — behind one payment coordinator, so the checkout flow doesn't know or care which the customer picked.
  • A cloud relay service, Dockerized and deployed separately, issuing one-time expiring links for phone transfer, with a LAN-hosted fallback when the kiosk is offline.
  • A self-updater that polls GitHub Releases, verifies checksums, and swaps builds with rollback while keeping the app running.
  • A locked-down shell — fullscreen and topmost, re-grabbing focus from printer driver popups, with a hidden admin dashboard behind a tap pattern and PIN for pricing, CSV reports, and hardware status.

HPV2026Freelance

A print shop's website and orders, run by the owner

The website and order system for HiPive, a printing and merchandise business in Makati. Customers choose a product, upload their artwork, and track the quote and status online instead of by phone. The owner runs orders, site text, services, and photos from one admin page, with no developer in the loop. Live at hipive.com.

A small print shop usually takes orders over Viber, and the artwork shows up as a 40 MB PDF somewhere in a chat thread. The goal was to move all of that onto a site one owner could run alone: no servers to look after, running costs close to zero, no customer details visible to anyone who happens to have an order number, and no rebuild or deploy just to change a price or add a photo.

  • A serverless order API: one AWS Lambda behind a Function URL, with no runtime dependencies. Orders are stored in DynamoDB, and email alerts go out through SES with the customer as reply-to, so the owner can answer with one click.
  • Artwork goes straight to S3 from the browser on a short-lived presigned URL. Files are capped at 50 MB and signed to a fixed content type, so the uploader can't change how a file is stored, and large files never pass through the API.
  • Content the owner edits without a deploy. Site text, services, the hero carousel, an announcement bar, and the photo gallery live in content.json and gallery.json on the site bucket. The admin page writes them through the API, and saving publishes instantly. The site ships built-in defaults, so a missing or broken file never blanks the page.
  • Photos resized in the browser. The admin page redraws each photo on a canvas before upload, which shrinks it and strips camera metadata such as location. Photos then go straight to S3 on a presigned URL and are served through CloudFront with permanent caching.
  • A customer status page that looks up an order number and shows the status, quote, and payment link. It returns no name, phone number, or email, so a guessed number reveals nothing. Order numbers carry 40 random bits and leave out look-alike characters such as 0/O and 1/I.
  • An admin key with brute-force protection. The key lives in SSM Parameter Store, is compared in constant time, and is re-read every minute, so rotating it needs no redeploy. Ten wrong attempts from one IP address lock that address out for 10 minutes, tracked in DynamoDB with automatic expiry.
  • No lost orders, no lost content. If the order API is unreachable, the form offers the same order as a pre-filled Viber, Messenger, Telegram, or SMS message. Both buckets keep 90 days of versions, and the deploy script never touches the owner's files.
  • A React 19 and TypeScript front end built with Vite, served from S3 through CloudFront. A CloudFront Function maps clean URLs such as /admin, and there is a branded 404 page. Hashed assets are cached permanently and pages are never cached.

JFM2026Side projectIn progress

Monitoring coin-operated WiFi across many sites

A central Spring Boot server for piso-WiFi vendos (coin-slot hotspot machines) running JuanFi, an open-source project I forked, and for the MikroTik routers behind them. It gives one dashboard for uptime, sales, active users, and remote restarts across every site. The server core is built and tested; the dashboard and push alerts come next.

Two constraints shaped the design. The sites run on consumer internet with no public IP, so nothing can connect in to them. And the vendo firmware's v4.3 API has no documentation, so I recovered it from the release binaries. Because of this, each router checks in to the server over HTTPS every 60 seconds, forwards the raw vendo readings, and gets any pending commands back in the response.

  • The router only relays. It forwards raw strings, and all parsing happens on the server, with unit tests against captured fixtures. A firmware quirk then needs one server deploy, not a new script on every router.
  • A command queue with acks and expiry. A partial unique index in PostgreSQL allows only one open restart per device, so a double-tap can't reboot a machine twice.
  • Sales deduplicated in the database. Routers retry over flaky uplinks, so each sale is keyed on voucher and router timestamp and inserted with ON CONFLICT DO NOTHING.
  • Per-site tokens and an ingest rate limit. Deleting a site or vendo keeps its sale, alert, and command history.
  • Tested against real infrastructure. Integration tests run on PostgreSQL through Testcontainers, and a fake vendo and fake router drive the full check-in loop end to end.

SEC2026AdacaFreelance

Closing out a penetration test on an enterprise platform

A freelance Java security engagement for an enterprise software vendor — remediating OWASP-class findings and penetration-test results, and re-architecting how the edge server signs its tokens.

Most scanner output is noise. The real work is deciding which findings are genuinely reachable in the codebase in front of you, then fixing those without breaking a platform its customers depend on. I do both halves — the triage and the remediation.

The token-signing problem

The edge server signed its JWTs with HS256 — a symmetric algorithm, where one secret both signs and verifies. Every service that needed to check a token therefore held the key that could mint one, so compromising any single service would let an attacker forge valid tokens for all of them. The same arrangement carries the algorithm-confusion risk a penetration test looks for, where a manipulated alg header turns a verifier into a forger.

I moved signing to RS256. The authorization server now holds the private key and is the only thing that can sign; everything downstream fetches the public key from a JWKS endpoint and can only verify. Key rotation stopped being a coordinated secret-redistribution exercise across every service.

The rest of the engagement

  • Remediated OWASP-class findings across Java services — injection, XSS, CSRF, and insecure deserialization — prioritized by whether they were genuinely reachable.
  • Pinned accepted signing algorithms explicitly, so a manipulated alg header can't downgrade verification or bypass it outright.
  • Encryption at rest and in transit using the Java Cryptography Architecture and Extension.
  • Certificate, SSL/TLS, and key management.
  • Upgraded vulnerable libraries and frameworks, and closed out findings raised by penetration testing.
  • Static and dynamic testing wired into the pipeline as gates rather than reports.
  • Triaged findings across Checkmarx, Fortify, and SonarQube — three scanners with three different noise profiles. Knowing what each one over-reports before you spend a day chasing it is most of the job.

I've since packaged that triage rubric as a public tool: an AI agent and skill that decides whether a scanner finding is realistically exploitable in your codebase. It works with Checkmarx, Fortify, SonarQube, Snyk, Semgrep, CodeQL, or plain SARIF, and backs each verdict with a source-to-sink trace, file and line references, and a benign proof-of-concept payload, rather than restating the scanner's verdict — github.com/lslaoang/appsec-agents

AUTH2021—2025Accenture

One authentication story across a whole service estate

Consistent OAuth2 / JWT authorization for services sitting behind a reverse proxy, backed by Azure AD.

When services each invent their own identity handling, you get inconsistent enforcement and no auditable answer to "who could call this?". I designed the flow so tokens are validated once at the gateway against the identity provider's signing keys, and services enforce scopes rather than re-implementing authentication.

For a dashboard app at the same bank, a software architect needed to choose a sign-in method. I built the proof of concept that informed the choice: SSO over SAML, and a reverse proxy written as a Spring Boot app, so both options could be compared working rather than on paper.

I have a public reference implementation of this pattern — Azure AD on-behalf-of token exchange with Spring Security and MSAL: github.com/lslaoang/Intune-WebApp
